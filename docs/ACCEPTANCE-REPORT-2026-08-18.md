## 一、原始验收结论（实施前）

**结论：不通过。**

安装包能够启动，大部分页面能够打开，类型检查、单元测试和生产构建均通过；但核心业务链路仍不能闭环：

1. 复杂任务可以进入澄清和审批，但批准后因没有项目绑定而派工失败，任务数和成果数均为 0。
2. 简单任务在执行引擎不可用时仍可点击安排，界面进入无法说明原因、无法取消的“安排中”状态。
3. 规划器没有根据老板的真实业务边界进行澄清，也没有按要求自动组织产品、设计、开发、测试协作。
4. 即便未来任务可以完成，Windows 上常见 `npm` 交付产物的“一键运行”当前仍会报 `spawn EINVAL`。
5. QQ 连接和本地语音存在“看起来可以配置或测试成功、实际没有真实能力”的误导性功能。

因此当前版本只能判定为“应用外壳及部分基础设施可运行”，不能判定为“AI 公司工作流可用”。

## 二、目标流程与实际结果

| 阶段 | 目标行为 | 本次结果 |
|---|---|---|
| 老板下令 | 从一个明确入口用自然语言交代任务 | 有多个入口，简单/复杂请求可被分类 |
| 边界澄清 | 简单任务直达；复杂任务围绕业务缺口多轮确认 | 分类基本正确，但问题高度模板化，未真正澄清业务边界 |
| 方案确认 | 对需要比较的事项给出真实备选方案后再确认 | 未比较两种技术方案，只询问“单人/团队”和预算档位 |
| 自动分工 | 根据任务自动选择部门、员工、依赖和复核关系 | 明确要求多角色协作时仍推荐单人，只生成 Cordis 的一个节点 |
| 执行 | 派工前检查项目、工作目录、引擎、权限是否可用 | 缺少前置检查；规划派工失败，直接派工会卡在安排中 |
| 监管 | 通过任务中心、待办和渠道看到一致状态并可恢复 | 状态互相矛盾；失败信息分散，任务中心没有恢复入口 |
| 交付 | 给出成果、目录、预览、启动方式、截图和说明 | 因无任务完成而未能端到端验证；Windows npm 一键运行已确认失败 |
| 渠道回传 | 绑定主调度和渠道后发送结果并支持远程监管 | 未能走到交付阶段；QQ 仍为伪连接，不具备验收条件 |

## 三、P0 核心流程阻断

### P0-01 规划批准后无法派工：规划会话没有项目绑定

**复现路径**

1. 创建复杂任务：“从零构建可本地预览的工作室官网，产品、设计、前端和测试协作，比较两种技术方案，确认后分阶段实现，最终交付目录、启动方式和截图”。
2. 完成问题回答，生成计划并批准。
3. 点击派工。

**实际结果**

```text
NEEDS_INPUT -> DRAFT -> PROPOSED -> APPROVED -> dispatch FAILED
PROJECT_BOUNDARY: planning session <id> has no project binding
tasks = 0
deliverables = 0
```

兼容规划页面可以创建规划会话，但创建表单没有项目选择；主进程派工又强制要求项目绑定。用户可以完整走完回答、生成、审批，直到最后一步才得知前面无法执行。

**影响**

- 复杂任务主链路完全不可用。
- “已批准”给老板造成已经可以执行的错误预期。
- 失败后任务中心仍显示“暂无任务”，无法在原流程中修正项目或重新派工。

**证据**

- `tmp/ux-audit/scenario-artifacts/planning-flow.json`
- `tmp/ux-audit/scenario-artifacts/05-planning-dispatch-result.png`

### P0-02 执行引擎不可用时仍允许派工，提交后界面无可理解反馈

测试时的真实状态为：

```text
executorAvailable = false
Managed Engine = SETUP_REQUIRED
launchable = false
authenticated = false
taskVerified = false
Quest = 模型不可用
```

但数字员工 Cordis 同时显示 `READY / idle`，用户仍能打开“安排任务”并提交。提交后弹窗变为“安排中…”，取消按钮被禁用，没有任务生成，也没有引擎不可用或等待选择目录的说明。

本场景所选项目没有工作目录，底层很可能正在等待原生目录选择器；即使如此，产品界面也没有告诉用户当前在等待什么，并把取消入口禁用了。对老板而言，这等同于卡死。

**影响**

- 简单任务虽然被正确判定为无需规划，但仍无法可靠执行。
- 用户不知道应该配置模型、选择目录、等待，还是重启应用。
- 无超时、无失败态、无重试或跳转到配置的就地入口。

**证据**

- `tmp/ux-audit/scenario-artifacts/02-direct-task-submit-state.png`
- `tmp/ux-audit/scenario-artifacts/03-direct-task-result.png`
- `tmp/ux-audit/scenario-artifacts/scenarios.json`

### P0-03 Windows 上交付产物“一键运行”对 npm 项目必然失败

交付功能会把 `npm` 解析为 `npm.cmd`，随后通过 `execFile(..., shell: false)` 启动。与产品相同的调用方式在本机 Node.js v24.18.0 实测结果为：

```text
Error: spawn EINVAL
code: EINVAL
syscall: spawn
```

这会直接影响 React、Vue、Vite、Node.js 等最常见的小公司交付场景。当前主流程尚未产生真实 manifest，因此没有完成 UI 端到端点击，但底层实际调用已在目标 Windows 环境复现失败。

相关实现位置：`src/main/ipc.ts:620-637`、`src/main/ipc.ts:2355-2375`。

**影响**

- “直接打开运行或本地预览”的核心交付承诺不成立。
- Renderer 的运行按钮逻辑只有 `finally`，IPC 拒绝时可能只恢复按钮而没有明确失败 Toast。

## 四、P1 操作与业务逻辑问题

### P1-01 澄清问题是治理模板，不是业务澄清

仿真结果：

| 场景 | 老板明确要求先确认的内容 | 系统实际提问 |
|---|---|---|
| 工作室官网 | 两种技术方案、目标客户、实施边界 | 执行组织方式、预算档位 |
| 小型电商 | 目标客群、预算、竞品口径 | 执行组织方式、预算档位 |
| 内容工作室 | 平台、受众、品牌禁区 | 执行组织方式、预算档位 |
| 高风险文件与外发 | 删除、覆盖、发送分别审批 | 风险策略、预算档位 |

系统能识别“长任务、比较方案、分阶段、不可逆操作”等信号，但只是把它们显示为门禁标签，没有把信号转化成具体、可回答、会改变执行计划的业务问题。

这与“主调度像 superpower 一样补充边界”的目标差距较大：老板仍要自己知道系统缺什么，并手动写进“补充其他约束”。

### P1-02 明确要求多部门协作时仍推荐单人执行

官网场景明确写了“产品、设计、前端和测试分工协作”，系统却：

- 推荐 `single / 单人负责`。
- 只选择 Cordis。
- 团队成员为空。
- 只生成一个 DAG 节点。
- 没有产品、设计、开发、测试角色，也没有阶段依赖或交叉验收。

系统识别出跨角色和分阶段诉求，却给出与诉求相反的默认推荐，容易让老板在不细看时直接批准错误组织方案。

### P1-03 计划没有形成可验收的交付合同

老板要求源码目录、README、启动命令、桌面截图、手机截图，计划中的预期成果却退化为：

```text
Markdown 工作成果或结构化结果
```

节点验收条件只有：

```text
完成老板请求并提交可验收成果。
```

这是循环定义，不可用于验收，也不能约束数字员工真正生成文件、截图或可运行项目。预算数字看起来很精确，但交付物和验收标准非常模糊，属于治理信息重、结果约束轻。

### P1-04 全局状态互相矛盾，用户无法判断公司是否能工作

同一时刻界面显示：

- 顶栏：`在线`
- Cordis：`READY / idle`
- Quest：`模型不可用`
- 引擎：`SETUP_REQUIRED`
- 执行器：`executorAvailable=false`
- Quest 设置：`主员工 已绑定`

“在线”到底表示应用进程、网络、渠道、模型还是执行能力没有说明；`READY` 也没有体现员工所依赖的引擎不可用。用户看到绿色状态后仍无法执行任务，可信度会快速下降。

### P1-05 失败反馈被分散到不同模块，任务中心看不到规划失败

规划派工失败后：

- 任务中心仍显示 0 个任务和“暂无任务”。
- 左侧“待我处理”出现数字角标 1。
- 当前页没有解释角标与本次失败的关系。
- 没有“绑定项目并重试”或返回失败规划的入口。

用户必须猜测错误可能藏在另一个模块。核心流程的异常不应只通过角标间接表达。

### P1-06 项目创建成功后，默认页面仍呈现“没有项目”的视觉结果

创建项目后同时出现：

- Toast：`项目已创建`
- 页面摘要：`1 个进行中`
- 经营看板：`还没有可分析的项目`
- 主操作仍是再次“新建项目”

从数据语义看，可能是新项目还没有可分析的任务或成果；但文案和默认视图让用户认为刚创建的项目消失了。用户必须自行切换到“项目清单”才能确认项目存在。

**证据**：`tmp/ux-audit/scenario-artifacts/01-project-created.png`

### P1-07 QQ 是伪连接，会在没有真实 Gateway/WebSocket 时自动显示在线

连接中心把 QQ 标记为“演示”，但仍提供“开始连接”，并提示真实环境会唤起 Gateway/WebSocket。实际逻辑只是：

1. 将数据库状态改成 `CONNECTING`。
2. 等待 1.2 秒。
3. 无条件改成 `ONLINE`。

没有建立 QQ 连接、没有认证、没有心跳、没有收发验证。即使有“演示”标签，真实风格的配置文案和绿色在线状态仍会误导用户认为渠道已接通。

相关实现位置：`src/renderer/src/pages/Channels.tsx:49-50,376`、`src/main/services/channelManager.ts:71-79`。

### P1-08 本地语音不可用，但仍可选择，并存在伪成功自检

设置页提供“仅本地（离线，数据不出本机）”选项，同时又以小字说明尚未实现。逻辑上只要指定模型目录存在：

- `resolveProvider()` 会判定本地 Provider 可用。
- `test()` 会返回 `ok: true`。
- 真正 `startLocal()` 时固定抛出“本地离线识别尚未实现”。

这不是单纯的“开发中”提示，而是自检状态与真实执行结果矛盾。未实现的模式不应作为可选择的工作模式，更不能返回测试成功。

相关实现位置：`src/renderer/src/pages/Settings.tsx:474-484`、`src/main/services/voiceService.ts:187-206,425-432`。

### P1-09 新安装会预置“已启用但未配置”的 MCP 服务器

空数据库会插入 8 个 MCP 服务器并统一写入 `enabled=1`，其中包括：

- 文件系统路径固定为 `E:/AIBox/workspaces`。
- SQLite 路径固定为 `E:/AIBox/data/business.db`。
- GitHub Token 是 `<YOUR_TOKEN>`。
- Brave Key 是 `<YOUR_KEY>`。
- 多个服务依赖首次运行时通过 `npx -y` 下载。

这些记录是模板配置，不是真实可用连接，却以启用状态进入系统。固定 E 盘路径也不适用于没有 E 盘或未选择该目录的用户。这与“禁止 Mock/避免误导”的目标冲突。

相关实现位置：`src/main/services/seed.ts:19-77`。

### P1-10 升级用户的演示数据仍会混入真实列表

新版本不再主动创建虚构项目、员工和任务，这是正确的；但旧版 `is_demo=1` 数据只从首页统计中排除，仍会显示在列表页，直到用户进入设置手动清理。

这会产生两个问题：

- 首页统计与员工/任务/项目列表数量不一致。
- 老板可能把旧演示员工或任务当成真实对象继续操作。

清理入口只能缓解问题，不能消除演示数据与真实业务数据混在一起造成的误导。

## 五、P2 UX、重复模块与过度设计

### P2-01 22 个一级导航项压过了核心流程

侧栏共有 22 个一级页面：

```text
Quest、项目中心、待我处理、经营概览、办公室、任务中心、成果库、项目知识库、
经营自动化、专家团、工作流、多机协同、数字员工、员工市场、引擎中心、插件中心、
连接中心、执行监控、手机控制台、用量统计、系统状态、设置
```

首屏侧栏必须滚动，靠后的配置项被截断。老板最需要的“下令、确认、看进度、收成果”没有形成四个清晰入口，而是与大量低频治理和技术模块处于同一层级。

### P2-02 同一工作链路被拆散到多个相近模块

用户需要在以下概念间自行建立关系：

- 下令：Quest、办公室、数字员工详情里的安排任务、兼容规划。
- 规划与执行：Quest、兼容规划、专家团、工作流、任务中心、执行监控。
- 结果：任务详情、成果库、项目中心、项目知识库。
- 可用性：顶栏在线、系统状态、引擎中心、Quest 连接设置、执行监控。

这些模块未形成由任务驱动的单一路径，反而要求老板理解内部架构。尤其“兼容规划（Local CLI）”仍保留完整创建和派工能力，却又提示真正入口在 Quest，造成两套调度心智。

### P2-03 技术状态和内部术语直接暴露给老板

界面出现 `DSH / Cordis`、`Provider`、`Base URL`、`SETUP_REQUIRED`、`revision`、`DAG`、`receipt`、`token` 等术语。对开发者有诊断价值，但对“老板下令”的主要角色不是行动语言。

老板真正需要知道的是：当前能否工作、缺少什么、由谁处理、点击哪里恢复。现有文案把系统内部状态展示出来，却没有给出统一结论。

### P2-04 空页面占用大面积空间，但缺少下一步行动

- 任务中心空表只有“暂无任务”，没有“去下令”或“修复执行环境”。
- 规划失败后任务中心仍是相同空表。
- Quest 模型不可用时主区域大面积空白，设置表单挤在右侧。
- 新项目经营看板为空时仍提供“新建项目”，没有引导用户为已建项目选择目录或下达首个任务。

视觉上整洁，但无法帮助用户完成下一步。

### P2-05 “在线”状态过于显眼且语义不完整

顶栏绿色“在线”在每个主页面都非常突出，却不代表 AI 可以执行、渠道已连接或模型已认证。它制造了最强的正向状态信号，随后用户才在其他页面看到“模型不可用”。这是状态层级设计问题，不只是文案问题。

### P2-06 核心失败需要跨页排查，恢复成本过高

一次任务失败可能要求用户依次检查项目目录、Quest Provider、引擎中心、待我处理、任务中心和执行监控。系统没有把这些依赖汇总成一次派工前检查，也没有在失败位置直接给出恢复路径。

对于个人工作室，这种操作成本接近运维平台，不像“老板只需下令”的 AI 公司。
